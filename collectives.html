集合通信 · COLLECTIVES

all-reduce
是一个动作名

broadcast、scatter、gather、reduce、all-gather、reduce-scatter、all-to-all —— 这不是七八个概念，是同一件事的七八种搬法。

一群 GPU 手里各有一堆数，现在要把这些数弄到该去的地方。名字听着吓人，其实每个名字只回答两个问题。

问题一
搬完之后，谁手里有结果？
只有一张卡有 每张卡都有

名字前面挂 All- 的，就是「人人都有一份，而且是同一份」。
没挂的，结果只落在一张卡（叫 root）上。

问题二
路上要不要做算术？
只搬，不算 边搬边加

名字里带 Reduce 的，路上会把各卡的数对位相加（也可以是 max / min / 求平均，加法最常用）。
不带的，只是搬运：拼起来，或者切开发走。

两个问题 2×2，就是这一族名字的全部结构。剩下一个 all-to-all 是唯一的例外 —— 它根本不做算术，它在做别的事（第 5 节）。

2

名字是拼出来的，不用背

四个词根，一个前缀。拼一下就知道这个动作在干什么 —— 这比记住八张图有用得多。

四个词根：数据的走向

Broadcast= 一个人的东西，复印给所有人
Scatter= 一个人的东西，切开发给所有人
Gather= 所有人的东西，拼起来收到一处
Reduce= 所有人的东西，对位相加成一份

一个前缀：结果给谁

All-= 每张卡都拿到完整的结果

于是：

All+Gather→拼好的整条，人人一份
All+Reduce→加好的和，人人一份
Reduce+Scatter→加好了，但每人只拿一格

注意 Reduce-Scatter 的顺序：先加，再切开分。所以每张卡拿到的那一格，是全部四张卡在这一格上的和。

4

all-reduce：为什么是出现最多的那个

「每张卡都要拿到全体的和，而且必须是同一份和。」
只要有这个需求，答案就是 all-reduce。

数据并行的梯度

N 张卡各看不同的数据，各算出一份梯度。要让 N 份模型参数在更新后依然一模一样，就必须先把 N 份梯度合成同一份 —— all-reduce。

每步一次，量 ≈ 2 × 梯度大小。

张量并行的每一层

一个矩阵乘被按列切到 4 张卡上，每张卡只算出部分和。要得到完整结果，必须把 4 个部分和加起来发回每张卡 —— all-reduce。

Megatron 式切法下，一个 transformer block 前向要两次（attention 出口 + MLP 出口），反向还有两次。这就是张量并行只敢在机内 NVLink 上做的原因。

loss / 指标

打印一个全局 loss、算一次全局 token 数、统计梯度范数做裁剪 —— 都是「各卡有个数，要合成一个每卡都认的数」。

量极小，但同步的代价一样：得等所有卡到齐。

一个容易被忽略的细节：求和还是求平均

all_reduce 默认做的是 SUM。而数据并行要的是平均梯度 —— 因为 loss 本身是 batch 内取平均的，N 张卡加起来就相当于把 loss 放大了 N 倍。

# 手写 DP 的时候，这个除法不能忘
dist.all_reduce(grad, op=dist.ReduceOp.SUM)
grad /= world_size          # ← 忘了它，等于学习率悄悄乘了 N

# 或者直接让通信库做平均
dist.all_reduce(grad, op=dist.ReduceOp.AVG)

另外注意：浮点加法不满足结合律。不同算法（ring / tree）、不同卡数下加法顺序不同，结果会有末位差异。所以「换了卡数 loss 曲线对不上最后几位」是正常的，不是 bug。

5

all-to-all：它不聚合，它转置

前面七个动作里，数据要么被复制，要么被加起来。all-to-all 两样都不做 —— 数据总量一个字节都没变，只是换了个人拿。

关键在于换一种读法：把「4 张卡 × 4 格」这张表的列重新理解一下。

换之前：行 = 谁拿着

GPUi 手里第 j 格，意思是「我手上这块，是要给 GPU j 的」。

换之后：列 = 谁拿着

GPUj 手里第 i 格，意思是「这块是 GPU i 给我的」。

实验台 · all-to-all = 转置
GPU

看数字：转置前 GPU1 手里是 10 / 20 / 30 / 40（都是 2 位数 —— 都是自己的货）； 转置后 GPU1 手里是 2 / 20 / 200 / 2000（位数各不相同 —— 四张卡各给它一块，而首位数字全是 2，都是「给 1 号」的那一格）。

对角线上的格子从来不动（自己给自己的那块），所以每张卡实际只需要发出 (N−1)/N · S。

工程上这件事有个更常用的说法：换一个维度切数据（re-shard）。原来按「谁的数据」切，现在按「谁负责算」切。总量不变，只是切法换了个轴 —— 这就是 all-to-all 的全部含义。

6

all-to-all 用在哪：MoE 的 token 路由

最典型的场景。MoE 层里有一堆「专家」（每个专家就是一个 MLP），专家太多装不下，于是一张卡放一个专家。

但 token 是按数据切的 —— GPU0 手上的 token，router 说它该去 3 号专家。数据在 0 号卡，专家在 3 号卡。只能把 token 送过去。

实验台 · MoE 一层里的两次 all-to-all

一层 MoE = 两次 all-to-all

dispatch：把 token 送到专家所在的卡。
combine：算完把结果原路送回来 —— 因为残差连接要加回原来那个位置。

所以 MoE 的通信不是「多了一点」，是每层多两次全体交换。

为什么 MoE 特别怕负载不均

all-to-all 是集合操作：所有卡一起完成才算完。如果 router 把一半 token 都塞给 2 号专家，那么其他三张卡算完只能干等它。

这就是 MoE 训练里要设 capacity（每个专家最多收多少个，超了就丢）和加 load-balancing loss 的直接原因 —— 它们首先是通信问题，其次才是模型质量问题。

同一个套路还出现在别处：把长序列切给多卡做 attention 时，序列维度和 head 维度得换轴，用的就是 all-to-all（DeepSpeed-Ulysses 的做法）；推荐系统里巨大的 embedding 表按特征切开，各卡查到的向量要交换回各自的样本 —— 也是 all-to-all。凡是「数据切法要换个轴」，就是它。

7

先看笨办法：为什么不能「都发给 0 号卡」

要做 all-reduce，最直白的写法：所有卡把数据发给 0 号，0 号加完再发回去。逻辑没错，但它有个致命问题。

问题不在总量，在都压在一张卡的网口上。加卡不但没让通信变快，反而让 0 号卡的负担随 N 线性增长：8 卡时它要搬 7 份，1024 卡时要搬 1023 份。其余卡则在旁边闲着。

要修它，得让每张卡的网口都用上，而且每张卡搬的量还得跟 N 无关。这听起来不可能，但有办法。

8

Ring：为什么加卡不加通信量

把卡串成一个环，每张卡只跟右边的邻居说话，一次只发一格。转两圈就完成 all-reduce。

下面这个实验台一步一步走。格子里写的是「这一格目前累加了哪几张卡的数据」： 0+1 表示只加了两家， Σ 表示四家都加齐了。

GPU
格 0格 1格 2格 3

账算出来是这样

两个阶段各 N−1 步，每步发一格（S/N）。所以每张卡总共发出：

2 · (N−1)/N · S

N=2 → 1.0 S　　N=8 → 1.75 S
N=64 → 1.97 S　　N=1024 → 1.998 S

(N−1)/N 很快就趴在 1 上不动了 —— 8 卡和 8000 卡，每张卡每步搬的字节数几乎一样。这就是数据并行能撑到几千卡的根本原因。

顺带说：2·(N−1)/N·S 不只是「一种实现」，它就是 all-reduce 每卡通信量的理论下限 —— 没有算法能更省。

但它省的是带宽，不是延迟

ring 要走 2(N−1) 步，每一步都有固定开销。数据小的时候，时间全花在「跳来跳去」上，跟带宽没关系。

所以通信库还准备了别的算法：tree 把跳数压到 ≈2·log₂N（1024 卡：2046 跳 → 约 20 跳），代价是带宽利用率不如 ring；机内还有让交换机硬件直接做加法的路子。

选哪个不用你操心 —— NCCL 会按消息大小、卡数、拓扑自己挑。你要知道的只有一件事：小消息看跳数，大消息看带宽。

10

三个会真的咬到你的性质

一 · 所有卡必须都调，而且顺序一致

集合操作不是「发个包出去」，是一场需要全员出席的会。少一张卡调用，或者两张卡调用的顺序不一样，整个 job 就停在那儿，直到通信库的看门狗超时报 NCCL timeout。

# 经典死法：某张卡走了不同的分支
if loss.isnan():          # ← 只有 GPU3 上是 True
    continue              # ← GPU3 跳过了这次 all_reduce
dist.all_reduce(loss)     # ← 另外 7 张卡在这里等 GPU3，永远

# 同样会挂：只在 rank0 上打日志，而日志里有个 all_reduce
# 同样会挂：两张卡上 all_reduce 的张量形状/dtype 不一致

调试口诀：看到「所有卡都卡住、GPU 利用率 100% 或 0%、没有报错」，先怀疑 collective 没对齐，而不是怀疑数据加载。

二 · 一步的耗时 = 最慢那张卡

全员到齐才算完，所以一张降频的卡、一条坏网线、一个 rank 数据加载慢了 —— 整个集群一起等它。

规模越大，撞上一个慢节点的概率越高。这是大规模训练最主要的工程痛点，跟算法无关。

三 · 通信可以藏在计算后面

反向传播是从后往前算的，最后几层的梯度先出来。DDP 不等全部算完，而是把参数分桶，一个桶满了就立刻开始 all-reduce，跟前面几层的反向重叠跑。

所以「通信占多少时间」和「通信拖慢多少」是两件事 —— 藏得好的话，前者不小，后者可以接近零。

一页带走

1

名字是拼的，不是背的。All- = 人人拿到完整结果；Reduce = 路上对位相加；Gather = 拼起来；Scatter = 切开发走。看到新名字先拆词。

2

all-reduce = reduce-scatter + all-gather。它是全家唯一走两趟的，所以每卡通信量是 2·(N−1)/N·S，别的都是一趟 (N−1)/N·S。

3

all-to-all 不聚合也不复制，它是转置。数据总量不变，换的是「按哪个轴切」。MoE 的 token 路由、序列并行换轴、分布式 embedding 查表，全是它。

4

ring 的意义是「加卡不加通信量」。(N−1)/N 迅速趋近 1，所以每卡搬的字节数跟 N 几乎无关 —— 而中心汇总式的写法，root 的负担随 N 线性增长。

5

大消息看带宽，小消息看跳数。ring 省带宽（2(N−1) 跳），tree 省跳数（≈2log₂N 跳）。库会自己选，你只要知道它在权衡什么。

6

集合操作是全员会议。少一张卡调用就 hang；一步的耗时等于最慢那张卡。这两条比通信量本身更常成为线上问题。

一堆 GPU 之间发生的所有事，说到底只有三种：复制（一份变多份）、相加（多份变一份）、换个人拿（份数不变）。

那七八个名字，是这三件事的排列组合而已。
