1

直接回答：谁复制，谁切开

数据并行同时做两件事：复制模型，切分数据。两件事作用在不同的对象上。

模型 → 被复制

每张卡上都有一整份权重，也就是模型的全部权重。四张卡就是四份一模一样的模型。

这些副本必须始终保持一样。第 3 节会解释同步过程。

代价：显存 × N（一份都没省）

数据 → 被切开

一个 batch 被切成 N 段，同一步里每张卡只看其中一段，各段不重叠。下一个 epoch 重新 shuffle 后，同一条样本可能被分到另一张卡。

所以每张卡上跑的 batch 是「小 batch」，合起来才是你在配置文件里写的那个 global batch。

收益：每步吃掉的数据量 × N

那个最容易搞混的公式

# 你在配置里写的三个数，乘起来才是「真正的 batch size」
global_batch = per_device_batch × N_gpus × grad_accum_steps
                     ↑                  ↑              ↑
              每张卡一次看多少      切成几份       同一张卡重复几轮
                （空间上切）      （空间上切）      （时间上切）

# 例：per_device=8, 8 张卡, accum=4
global_batch = 8 × 8 × 4 = 256   # 优化器每 256 条样本才走一步

很多人调不好模型是因为只改了 per_device_batch，以为那就是 batch size。它只是 global batch 的 1/N。换机器（卡数变了）而不动这个数，等于悄悄改了 batch size —— 学习率立刻就不对了（第 10 节）。

2

为什么数据「不能」复制

假设每张卡都拿到同一份数据，结果会变成下面这样。

如果数据也复制，每张卡会算出相同的梯度。

四份梯度完全相同，平均以后仍是原来的梯度。没有新信息进入模型，计算成本却变成 4 倍。

因此 DP 必须让每张卡看到不同的数据。数据切开后，各卡得到不同的梯度；把它们平均，才等价于处理了更大的 batch。

⚠️ 一个常见错误是给每个 rank 使用相同的 data sampler（DistributedSampler 没设 / seed 没错开）。训练仍能运行，loss 也会下降，但 8 张卡实际在重复 1 张卡的工作，而且不会报错。

3

一步里到底发生了什么

DP 的一整步有四个动作。前三个由各卡独立完成，第四个需要全员同步。

它平均的是梯度，不是权重

常见误解是「各卡各自训，最后把权重平均一下」。那是另一个东西（叫 model averaging / local SGD），收敛性质完全不同。

DP 每一步都平均梯度，因此各卡的权重在每次更新后都保持相等，不需要在训练结束时再合并。

通信其实藏在反向里

反向传播从最后一层往前计算，因此最后几层的梯度先完成。PyTorch DDP 会把参数分成若干 bucket；一个 bucket 就绪后立即开始 all-reduce，同时继续计算前面各层的梯度。

于是通信和计算重叠，第 3 步的大部分时间被藏在第 2 步里 —— 这也是 DDP 比老式 DataParallel 快得多的原因。

4

凭什么这样是对的

DP 与单卡大 batch 等价，依据是平均梯度等于平均 loss 的梯度。所以「4 卡 × 每卡 8 条」和「1 卡 × 32 条」在数学上是同一件事。

# loss 定义成 batch 内每条样本 loss 的平均值（几乎所有框架的默认）
L(θ) = (1/32) · Σi=1..32 ℓi(θ)

# 求导是线性的，所以可以先按卡分组求和，再合起来
∇L = (1/32) · Σi=1..32 ∇ℓi
   = (1/4) · [ (1/8)ΣGPU0∇ℓ + (1/8)ΣGPU1∇ℓ + (1/8)ΣGPU2∇ℓ + (1/8)ΣGPU3∇ℓ ]
   = (1/4) · [ g₀ + g₁ + g₂ + g₃ ]
              ↑ 这四个正好就是每张卡自己算出来的梯度

# 所以 all-reduce 求「平均」而不是「求和」—— 因为 loss 本身就是平均
ḡ = mean(g₀, g₁, g₂, g₃) = ∇L    ✅ 逐比特意义上的同一个数学量

这就是为什么 PyTorch DDP 默认对梯度取 mean 而不是 sum。如果它 sum，梯度会凭空放大 N 倍，等价于把学习率偷偷乘了 N。

在上述前提下，DP 与单卡大 batch 计算的是同一个梯度。

DP 可以缩短每一步的计算时间，也能让一步处理更多数据。除第 5 节列出的情况外，它不改变优化轨迹；同时，它也不会减少单卡上的模型状态显存。

5

这个恒等式会在哪里破

上面的推导有个前提：每条样本的 loss 只跟它自己有关。绝大多数情况成立，但有三个地方不成立 —— 而它们都不会报错，只会让你的多卡结果和单卡结果对不上。

BatchNorm

BN 的均值/方差是在 batch 内跨样本算的。切开数据后，每张卡只用自己那 8 条算统计量 —— 这跟单卡用 32 条算不是同一个数。

修法：SyncBatchNorm（统计量也 all-reduce），代价是多一轮通信。

CNN 时代最大的坑

LayerNorm / RMSNorm

它们只在单条样本自己的特征维上做归一化，压根不看 batch 里的别人。

因此 batch 的切分方式不会影响统计量。Transformer 通常使用 LayerNorm 或 RMSNorm，也就避开了 BatchNorm 的这个问题。

天然安全，不用管

跨样本 loss

对比学习（CLIP / InfoNCE）里，一条样本的 loss 分母是整个 batch 的其他样本当负例。切开之后，每张卡只能看到 1/N 的负例。

结果：有效负例数悄悄缩了 N 倍，效果直接掉。修法是把 embedding 先 all-gather 起来再算 loss。

对比学习必踩

还有一个更蠢也更常见的：各卡 batch 不一样大

all-reduce 算的是「各卡平均值的平均值」。只有每张卡样本数相等时，它才等于「全局平均值」。

所以当最后一个 batch 凑不满、或者按 token 数动态组 batch 导致各卡条数不同时，样本少的那张卡上的每条样本会被赋予更大的权重。这就是 drop_last=True 存在的理由，也是变长序列训练里要按 token 数做归一化（而不是按条数）的理由。

7

ZeRO / FSDP：数据还是照原样切

这里最容易迷路：ZeRO 和 FSDP 明明在切模型，为什么还叫「数据并行」？因为它们对数据的切法跟 DP 一字不差 —— 变的只是「模型状态平时存在哪」。

为什么优化器状态最先被切

因为它最胖。bf16 混合精度 + Adam 下，每个参数要存：

2 B 权重 + 2 B 梯度
+ 4 B fp32 主权重
+ 4 B 一阶动量 m
+ 4 B 二阶动量 v
= 16 B / 参数

那 12 B 的 fp32 三件套占了 四分之三，而且只在第 4 步（更新）用到一瞬间 —— 平时留在本地是纯浪费。ZeRO-1 就是把它切了，几乎不加通信。

代价：通信从 2P 涨到 3P

ZeRO-1 / ZeRO-2 的通信量和纯 DP 一样（都是 2× 参数字节）—— 一次 reduce-scatter 把梯度归到各自负责的那份，一次 all-gather 把更新后的权重发回去。省显存不花钱。

ZeRO-3 多一笔：权重平时也不在本地，前向每层都要先 all-gather 拿权重。总通信量约 3× 参数字节，是纯 DP 的 1.5 倍。

所以升级路线是 ZeRO-1 → 2 → 3，能停就停
8

梯度累积 = 时间上的数据并行

如果你只有一张卡，也想要那个「大 global batch」，可以把 DP 从空间挪到时间上 —— 一张卡连续跑 N 遍，攒够了再更新一次。在 loss 归一化、随机性和跨样本运算一致的前提下，两者得到同一个平均梯度。

# 梯度累积：先把 loss 缩放处理对
for step, batch in enumerate(loader):
    loss = model(batch).loss / ACCUM   # ← 忘了这个，梯度就大了 ACCUM 倍
    loss.backward()                   # 梯度默认是「累加」到 .grad 上的
    if (step + 1) % ACCUM == 0:
        optimizer.step()
        optimizer.zero_grad()

除以 ACCUM 的作用，和 DP 里 all-reduce 取 mean 都是在把「求和」变回「平均」。DP 在卡之间做，累积在时间上做。若模型含 BatchNorm、跨样本 loss，或者两种跑法使用了不同的随机数，结果不一定逐值相同。

⚠️ 两者叠加时还有个细节：多卡 + 累积的中间几轮，应该用 no_sync() 跳过 all-reduce，只在最后一轮才同步。否则你会为一次更新做 ACCUM 次全集群通信，白白慢一大截。

9

通信账：为什么加卡不加通信

直觉上「N 张卡两两同步」应该是 N² 级别的灾难。ring all-reduce 的漂亮之处就是：每张卡要发的字节数，跟 N 几乎无关。

P = 梯度的字节数。N 一大，(N−1)/N 就趴在 1 上不动了 —— 所以 8 卡和 8000 卡，每张卡每步要搬的量几乎一样。DP 能撑到几千卡规模，全靠这个性质。

但「总量不变」≠「不痛」

7B 模型 bf16 梯度 = 14 GB，每步每卡要收发 ≈ 28 GB。这一坨必须在一步之内搬完，否则 GPU 就在干等。

这就是训练集群里网络是一等公民的原因：机内 NVLink（数百 GB/s）、机间 InfiniBand / EFA。把 DP 组拉到普通以太网上，通信立刻变成瓶颈。

每一步的速度由最慢那张卡决定

all-reduce 是集合操作：所有卡都到齐才算完。所以每一步的耗时 = 最慢那张卡的耗时。

一张降频的卡、一条坏网线、一个 rank 上数据加载慢了 —— 整个集群一起等它。规模越大，遇到一个慢节点的概率越高，这是大规模训练最主要的工程痛点。

DP 组越大，越怕长尾
10

DP 的扩展上限：critical batch size

增加 DP 卡数会增大 global batch。batch 超过 critical batch size 后，继续加卡通常不再缩短收敛所需的步数。

第一步：batch 变了，学习率必须跟着变

batch 大了，梯度的噪声小了，你就敢也需要迈更大的步子。业界的默认起点是 linear scaling rule：batch 乘 k，学习率也乘 k，前面配几个 epoch 的 warmup（因为训练最初期大步长会炸）。

这条规则出名，是因为 Goyal 等人 2017 年用它把 ResNet-50 / ImageNet 的 minibatch 从 256 推到 8192，在 256 张 GPU 上 1 小时训完，精度和小 batch 基线持平，8→256 卡的扩展效率约 90%。（Accurate, Large Minibatch SGD, arXiv:1706.02677）

推论：换机器要重新调学习率。你从 8 卡挪到 64 卡、per-device batch 没动，global batch 就悄悄大了 8 倍 —— 沿用旧学习率，训练要么爆炸要么原地不动。这是「同样的代码在新集群上就是不收敛」的头号原因。

第二步：过了某个点，加 batch 就白加了

直觉：梯度里既有「信号」也有「噪声」。batch 小的时候噪声占主导，多看样本能显著改善梯度方向 —— 加卡真的换来更快收敛。batch 大到噪声已经被平均干净之后，再多看样本对方向几乎没有改善，你只是在为同一步付更多算力。这个转折点被称为 critical batch size。（An Empirical Model of Large-Batch Training, arXiv:1812.06162）

global batch 达到临界规模后，剩余 GPU 通常用于 TP 和 PP。

当 DP 度数已经把 global batch 推到临界点，继续增加 DP 度数收益很小。此时可以用更多 GPU 切分模型，这就是 3D 并行（DP × TP × PP）的由来：

DP 度数被 critical batch size 卡住 → 剩下的卡拿去做 TP 和 PP。

七个要点

前面的内容可以归纳为下面七点。

01

模型被复制，数据被切开。「数据并行」这个名字说的就是被切的那个东西是数据。

02

每张卡需要读取不同的数据。如果每卡拿到同一份数据，梯度也会相同，平均后没有新增信息。

03

一步只有一个同步点：反向之后 all-reduce 把 N 份梯度平均（不是求和）。这一步保证了 N 份模型永远一模一样。

04

满足前提时，两种跑法得到同一个平均梯度。4 卡 × 8 条可以对应 1 卡 × 32 条。BatchNorm、跨样本 loss、随机数和浮点归约顺序都可能让实际数值出现差异。

05

纯 DP 不减少单卡的模型状态显存。分摊显存要用 ZeRO/FSDP（切状态）、TP（切矩阵）或 PP（切层）。

06

加卡会增大 global batch，因此需要重调学习率（linear scaling + warmup）；超过 critical batch size 后，继续加卡通常不再缩短收敛时间。

07

推理没有梯度，也没有训练时的 all-reduce。推理侧通常使用「多副本 + 负载均衡」；batch 由调度器根据请求动态组合。

训练和推理的差别

训练里，N 张卡靠每步一次 all-reduce 被绑成一个逻辑设备，一起走同一步；
推理里，N 张卡可以作为 N 个独立服务处理请求。

是否需要同步梯度，决定了两种系统的组织方式。
