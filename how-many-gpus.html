How many GPUs · 训练资源估算

「要几张卡？」
这问题没法直接回答

因为它不是一个问题，是三个独立约束的交集。
先搞清楚要问什么，再算——顺序反了就只能瞎猜。

Constraint A

显存

能不能跑起来？

硬约束。不满足就 OOM，一秒都跑不了。它给出卡数的下限。

Constraint B

算力

多久能跑完？

软约束。用钱换时间。它给出卡数的目标值——由 deadline 倒推。

Constraint C

互联

卡之间怎么切？

拓扑约束。决定能不能跨机、怎么跨，以及效率会掉掉多少。

答案 = max( 显存下限 , 算力需求 )，再被 互联拓扑 向上取整到整机

01先问清这几件事

按「不知道就根本没法算」排序。P0 缺一个，答案就能差一到两个数量级；P1 影响 30%–3× 的系数。

P0

训练方式

全参 + Adam / LoRA / QLoRA / 继续预训练 / DPO / PPO。这一项单独就能让答案差 16 倍——同一个 70B、4k 序列、两边都开梯度重算：全参 ZeRO-3 要 16 张 H100，QLoRA 一张就够。下面的估算器可以按这个设置切给你看。

P0

模型规模与架构

参数量 N、层数 L、hidden size h、head 数 a。还必须问是 dense 还是 MoE——MoE 显存看总参数，算力看激活参数，两者能差 10 倍。

P0

序列长度 + micro batch

激活显存的主要来源。长上下文场景下它是显存的主项，不是零头——70B 在 4k 序列下不开重算，激活单独就要 85 GB。

P0

数据量 × epoch

总 token 数 D 决定总 FLOPs。SFT 的 1 亿 token 和预训练的 1 万亿 token，差 4 个数量级——分钟级 vs 半年级。

P0

时间预算

一晚 / 一周 / 一个月。没有 deadline，就不存在「该买多少卡」这个问题——显存下限那几张卡总能跑完，只是慢。

P1

精度与优化器

bf16 / fp8 / base 权重 4-bit 量化；Adam（12 B/参数的状态）vs 8-bit Adam vs Adafactor vs SGD。换优化器能省下一半状态显存。

P1

手上有什么硬件

单机 8 卡还是多机？NVLink 还是 PCIe？跨机有没有 EFA / InfiniBand？这直接决定并行策略的可行域（见 06）。

P1

能接受多少额外算力开销

gradient checkpointing 用 +33% 算力换掉九成以上的激活显存（比例只跟层数有关，本页五个模型都在 90–93%）。愿不愿意换，会改变显存下限和时长两个答案。

这是最容易踩的坑：加卡能摊薄状态显存，摊不薄激活显存。激活是每个数据并行副本自己的，上面这三个 stage（ZeRO-DP）从头到尾没碰它。激活撑爆了只有三条路 —— 开 gradient checkpointing、上张量/序列并行、或者砍 batch 和序列长度。
一个容易被拿来反驳的细节：ZeRO 论文里确实有一个切激活的机制 —— ZeRO-R 的 P_a（Partitioned Activation Checkpointing），论文举的例子把 100B 模型的 33 GB 激活压到每卡约 2 GB。但它是沿张量并行组切的，不是沿数据并行组。也就是说：它靠的是 TP，不是靠加 DP 的卡。所以「加卡摊不薄激活」这个操作结论不变，只是别把它说成「ZeRO 完全没有切激活的手段」。

注意这是标称峰值之间的比较：两边的实际可达带宽都明显更低，所以它是个量级判断，不是实测吞吐。
但杀死跨机 TP 的不只是带宽。张量并行每层的前向和反向都要 all-reduce 激活：通信次数极多、每次的量不大、而且全部挡在关键路径上——这种模式对延迟比对带宽敏感得多。有实测数字的两侧：EFA 的单向 MPI 延迟约 15.5 µs，NVLink 的实测点对点延迟在 1–4 µs 量级。带宽差 9× 再叠上延迟差 4–15 倍，MFU 就崩了。

08容易搞错的几点

最常见的错

「参数量 × 2 = 显存」只对推理成立

推理只需要权重（bf16 = 2 B/参数）加 KV cache。全参训练是 16 B/参数——多出来的那 14 字节是梯度（2）和 Adam 的两个动量（8）加上 fp32 master 权重（4）。把推理的经验直接套到训练上，会低估 8 倍。

LoRA 的误解

LoRA 省显存，几乎不省算力

反向传播的 4ND 拆成两半：「传给输入的梯度」2ND 和「权重的梯度」2ND。LoRA 只省掉冻结权重那一半，6ND → ≈4ND，最好情况快 1.5 倍，不是 10 倍。而且激活照样要算全网络的——梯度得穿过每一层才能到 adapter。QLoRA 更是因为每次用权重都要反量化，wall-clock 常常比 LoRA 更慢。

加卡的边界

ZeRO-DP 不切激活，所以加卡有天花板

状态显存能被 G 摊薄到接近零，激活显存一点不变。当激活单独就超过卡容量时（70B / 4k 序列 / 不开重算 = 85 GB），加到一万张卡也照样 OOM。这时候要动的是 gradient checkpointing、TP、SP，不是卡数。上面的估算器把「激活」单独画成绿色，就是为了让这条线可见。（严格说 ZeRO-R 的 P_a 能切激活，但那是沿张量并行组切的 —— 还是不靠加 DP 的卡。）

MoE

MoE 的显存和算力看两个不同的参数量

显存要按 总参数量 算（所有 expert 都得驻留），算力按 每 token 激活的参数量 算。一个 8×7B 的 MoE，显存像 47B，算力像 13B。用同一个数字去算两边，两边都错。

厂商 spec

带 sparsity 的 TFLOPS 是 ×2 虚标，而且常常还是整机数

规格表里常常并排给「dense」和「with sparsity」两列，后者需要 2:4 结构化稀疏才能达到，常规训练用不上。估算一律用 dense 列。更坑的是有些表连单位都不是单卡：NVIDIA 的 HGX B300 把 FP16/BF16 写成 36 PFLOPS，那是整机 8 卡的sparse 值，脚注里才说「dense 是 sparse 的一半」—— 真正能用来估算的单卡 dense 峰值是 36 ÷ 8 ÷ 2 = 2.25 PFLOPS。少除一次，时间预估就乐观 2 倍；少除两次，乐观 16 倍。

被忽略的瓶颈

GPU 打不满，先看 dataloader 和存储

MFU 只有 15% 时，第一反应往往是「卡不够」，但真凶经常是数据加载跟不上、或者 checkpoint 写得太频繁。405B 存一份能续训的 checkpoint（权重 + 梯度 + Adam 状态，就是那 16 B/参数）= 6.5 TB，存取会实打实地挤掉训练时间。注意别跟「只导出 bf16 权重」的 0.8 TB 混了 —— 两者差 8 倍。加卡不解决这两个问题，只会让浪费按比例放大。

这一页的公式、常数和它们的出处
显存
  • 全参 Adam 混合精度 = 16 B/参数：fp16 权重 2 + fp16 梯度 2 + 优化器 12（fp32 master 权重 4 + 一阶动量 4 + 二阶动量 4）。出自 ZeRO 论文的 2Ψ + 2Ψ + KΨ, K=12。
  • 激活（单层，bf16）：s·b·h·(34 + 5·a·s/h)，出自 Korthikanti et al.《Reducing Activation Recomputation in Large Transformer Models》(arXiv:2205.05198) 式 (1)。系数 34 里没有 fp32 项（论文全程假设 16-bit，只有 dropout mask 是 1 字节），并且假设没有张量并行（有 TP 时变成 s·b·h·(10 + 24/t + 5·a·s/(h·t))）。
  • 34 这个系数是按 GPT-3 式的层推的：4h 的 GeLU MLP、全量 dropout、普通 MHA。本页的五个预设是 Llama / Qwen 系（SwiGLU 约 3.5h、无 dropout、GQA），真实系数大约在 30–40 之间浮动。34 是个合理的量级替身，不是这几个模型的精确常数。
  • 5·a·s/h 里的 a 是 query head 数，不是 KV head 数 —— GQA 不会削减这一项，因为每个 query head 仍各自产生一个完整的 s×s 打分矩阵。本页三个 GQA 预设填的都是 query head 数（1.5B 填 12 而非 2、70B 填 64 而非 8、405B 填 128 而非 8）。GQA 真正省的是 K/V 投影和 KV cache。
  • FlashAttention 消掉 5·a·s/h 这一项 —— 但严格说不是「消掉」，而是在反向里重算 attention 打分而不存它，用 FLOPs 换显存。论文给同类的选择性重算报的额外算力开销是 1.6–2.7%，很小，但本页的 6ND / 4ND 没有把它计进去。
  • 开 gradient checkpointing 后按「只存每层输入 + 正在被重算的那一层」估：2·s·b·h·L + 单层完整激活。注意「单层完整激活」跟着 FlashAttention 开关变 —— 关掉 FlashAttention 时，被重算的那一层照样会把 s² 的 attention 矩阵铺出来，所以那一项是 s·b·h·(34 + 5·a·s/h) 而不是 34·s·b·h。
  • QLoRA 的 base 权重按 4.127 bit/参数（NF4 的 4 bit + double quantization 的 8/64 + 32/(64·256) = 0.127 bit）= 0.516 B/参数。
  • LoRA / QLoRA 的可训练比例本页固定取 0.5%。这只是个代表值 —— rank 和作用在哪些层，能让它差好几倍。
  • LoRA / QLoRA 的冻结 base 权重在 ZeRO-3 下也按分片算（FSDP + QLoRA 那种做法）。很多简易实现是每卡各存一份完整 base，那样 stage 0–2 的下限会比本页显示的更高；stage 3 不受影响。
  • 每卡可用显存 = 标称容量 − 3 GB（CUDA context、NCCL 通信 buffer、显存碎片）。GB 按 2³⁰ B 算。
  • ZeRO-3 还需要临时 all-gather 一层的完整权重，本页未计入 —— 大模型上这一项不小。
算力
  • 总计算量 C ≈ 6·N·D（前向 2ND，反向 4ND）。一手来源是 Kaplan et al. 2020（arXiv:2001.08361）—— Chinchilla 只是引用它，不是原始出处。反向的 4ND 拆成「对输入求梯度 2ND + 对权重求梯度 2ND」，这个拆法在 Korthikanti et al. 附录 A 里有明文。
  • LoRA / QLoRA 跳过冻结权重的梯度，按 ≈4·N·D，理论上限是快 6/4 = 1.5 倍。实测远低于这个上限：LoRA 原论文（arXiv:2106.09685）在 GPT-3 175B 上报的是约 25% 提速（1.33×）—— 因为梯度还是得穿过每一层才能到 adapter。
  • 开 gradient checkpointing 多一次前向，+2·N·D，理论上 +33%。实测更高一些：Korthikanti et al. 对全层重算量到 39%，Chen et al. 2016 的原始论文量到约 30%。本页用理论值 33%。
  • 单卡 bf16 dense 峰值：A100 80GB SXM = 312 TFLOPS；H100 SXM ≈ 989 TFLOPS；H200 算力与 H100 相同（差别在 141 GB 显存和 4.8 TB/s HBM3e 带宽，对比 H100 的 3.35 TB/s）；B200 / B300 = 2250 TFLOPS。
  • 只有 A100 的 312 是 NVIDIA 直接印出来的 dense 值。H100 的 989 是推出来的：NVIDIA 现在的 H100 页面只印 sparse 的 1979 TFLOPS，dense 那份 PDF 已经改成留资下载，所以 989 = 1979 ÷ 2，按 NVIDIA 自己在 A100 / L4 / L40S / B200 / B300 上都明写的「dense 是 sparse 的一半」换算。p5 用的是 H100 SXM（不是 PCIe，也不是 94 GB 的 H100 NVL），所以取 SXM 这一档是对的。
  • B300 那个数是换算出来的：NVIDIA 的 HGX B300 规格表把 FP16/BF16 写成 36 PFLOPS，但那是整机 8 卡的sparse 值，脚注写着「Dense is ½ sparse spec shown」——所以 36 ÷ 8 ÷ 2 = 2.25 PFLOPS/卡。B200 的 BF16 也是这个数，Blackwell Ultra 提升的是 FP4（整机 dense 72 → 108 PFLOPS），BF16 没动。
  • B300 单卡显存本页取 268 GB（AWS 对 p6-b300 的口径）。NVIDIA 的 HGX B300 规格表给的是整机 2.1 TB，除以 8 等于 262.5 GB —— 两个来源差约 2%，对量级估算没影响。
  • MFU 校准数据：LLaMA-1 论文 Table 15 报的 A100-hours（7B / 1.0T = 82,432；65B / 1.4T = 1,022,362）反推得 45% 和 48%；PaLM 论文 Table 3 直接报 540B / 780B token 在 TPU v4 上 MFU 46.2%（同表还有 HFU 57.8%，那是把重算的 FLOPs 也算进去的另一个指标，别混）。
  • 40–48% 不是天花板。Korthikanti et al. Table 5 在同一代 A100 上报到 175B → 51.4%、530B → 56.0%、1T → 56.3% MFU，靠的是序列并行 + 选择性重算。所以「调好的 Megatron 只能到 48%」是错的 —— Megatron-LM 恰恰是打破这个区间的那篇。本页把 40–48% 定位成 LLaMA-1 / PaLM 那一代的水平，51–56% 才是已发表的最好成绩。
互联
  • NVLink：A100 SXM 600 GB/s、H100 SXM 900 GB/s。NVIDIA 标的这两个数本身就是双向合计（每方向各 300 / 450 GB/s）。
  • 跨机：AWS 对实例网络带宽的定义是每个方向各这么多（EC2 文档原文：「if an instance specifies up to 10 Gbps of bandwidth, that means it has up to 10 Gbps for inbound traffic and, simultaneously, up to 10 Gbps for outbound traffic」）。所以为了和 NVLink 同口径，本页按 标称 Gbps × 2 ÷ 8 ÷ 8 卡 换算成每卡双向合计 GB/s：p5 = 3200 → 100 GB/s；p4d = 400 → 12.5 GB/s。
  • 这个对比两侧都是标称峰值，不是可达吞吐，只够做量级判断：(a) 把整机带宽平均分给 8 卡，假设了每卡都能拿到均匀的一份 NIC，真实 collective 在 rail-optimized 织构上并不严格保证；(b) NVLink 的 900 GB/s 是 GPU 到 NVSwitch 的端口带宽，不等于 8 卡同时打满时的 all-reduce 有效带宽；(c) 两条路径的实际持续吞吐都明显低于各自峰值。另外 p5 的 3200 Gbps 里最多只有 800 Gbps 能走 IP 流量（EFA 与 IP 共享底层资源，这条是 p5/p5e 的口径，p5en 和 p6 的拆分不同）。
  • 延迟数字的来源和局限：EFA 的 15.5 µs 单向 MPI 延迟出自 AWS 2019 年 EFA 发布博客，是首代 EFA 的数字，已经旧了（第二代只公布了「端点延迟降低约 30%」的相对值，没给新的绝对值）。NVLink 的 1–4 µs 出自一篇同行评审 benchmark（arXiv:1903.04611，P100/V100 时代）—— NVIDIA 官方从未公布过 NVLink 的延迟数字，只说「低延迟」，所以本页不再声称它是「亚微秒级」（那个说法只对裸 SerDes 单跳成立，不是软件层可观测到的延迟）。
  • 07 节表格的显存用标称单卡容量。p4d 是 A100 40GB、p4de 是 A100 80GB。注意 AWS 文档把 L4 记作 22 GiB、L40S 记作 44 GiB，看着像是扣了开销，其实更可能只是十进制 GB 换成二进制 GiB：24e9 ÷ 2³⁰ = 22.35、48e9 ÷ 2³⁰ = 44.7，两个数都正好落在 AWS 的写法上。AWS 没有任何文档说那是给驱动或 ECC 留的余量，所以本页不作那种因果解释。
  • 07 节的 dense 算力：L40S = 362 TFLOPS（规格表写成 362.05 | 733*，前者就是 dense）；L4 = 121 TFLOPS（规格表只给 242*，脚注写「Specifications are one-half lower without sparsity」，所以要自己除 2）。这两张表用了相反的写法，是同一个坑的两种形态。g7e 的 RTX PRO 6000 Blackwell 没找到可靠的 bf16 dense 数，表里留空而不是填个估计值。
这个估算器不做什么

不建模 TP / PP 对显存和通信的影响，不算 KV cache（那是推理的事），不算 CPU offload，不算 checkpoint 的存储 IO，不考虑 MoE。它的用途是在开会时 30 秒内给出正确的量级和正确的追问，不是替代真机跑一次 profiling。

对方只给了一句话时，最少追回这三个：全参还是 LoRA？模型多大、序列多长？多少 token、什么时候要？
有了这三个，你能给出的就不是一个数字，而是「最少 X 卡跑得起来，要 Y 天内跑完需要 Z 卡」—— 有用得多。
